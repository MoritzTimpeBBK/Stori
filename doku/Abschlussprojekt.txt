USER STORY
----------
Eine User Story beschreibt eine fachliche Anforderung aus der Sicht einer Person, die das System nutzt.
Das Format ist immer:

  Als [Rolle] moechte ich [Ziel], damit [Nutzen].

Beispiele:
  Als Lernende moechte ich meine Note in einem Portal einsehen koennen, damit ich nicht auf den Postweg
  warten muss.
  Als Lehrkraft moechte ich sehen, welchen Faechern eine User Story zugeordnet wurde, damit ich die Bewertung
  transparent nachvollziehen kann.

User Story oder Ticket?
Im naechsten Schuljahr arbeiten Anwendungsentwickler eher mit User Stories (Was soll das System koennen?),
waehrend Systemintegratoren eher technische Tickets bearbeiten (Wie genau soll etwas umgesetzt werden?).
In diesem Projekt sagen wir deshalb meistens User Story, meinen aber immer beides.

DATENQUELLEN
------------
Im Projekt meint "Quelle" eine Datei in einem bestimmten Format, aus der eure Anwendung Daten liest.
Ihr simuliert damit, dass in der Realitaet verschiedene Tools ihre Daten unterschiedlich exportieren.

Konkrete Beispiele:
- Microsoft Planner kann Aufgaben als CSV exportieren
- GitHub Issues lassen sich als JSON exportieren
- Aeltere oder XML-basierte Systeme liefern XML-Dateien

Fuer euer Projekt benutzt ihr selbst erstellte Beispieldateien, die aber so aufgebaut sind, als kaemen sie
aus echten Tools.

Welche Formate benutzt ihr?

Format | Dateiendung | Kurzbeschreibung
CSV    | .csv        | tabellarisch, Felder durch Komma oder Semikolon getrennt
JSON   | .json       | strukturiert, weit verbreitet in Web-APIs
XML    | .xml        | strukturiert mit Tags, aelterer Standard

Mindestens zwei dieser Formate muessen unterschiedliche Feldnamen oder unterschiedliche Strukturen haben.
Genau das macht sie "heterogen".

DATENMODELL
-----------
Ein Datenmodell legt fest, welche Felder eine User Story in eurem System hat - unabhaengig davon, aus welcher
Quelle sie stammt.

Warum braucht man das?
Quelle A (CSV-Export aus Planner) hat ein Feld "Aufgabe". Quelle B (JSON-Export aus GitHub) hat ein Feld
"title". Beide meinen dasselbe. Im gemeinsamen Modell heisst das Feld bei euch z. B. "titel".

Beispiel fuer ein einfaches gemeinsames Modell:

Feld          | Typ   | Pflicht? | Erklaerung
id            | Text  | ja       | eindeutige Kennung
titel         | Text  | ja       | Kurztitel der User Story
beschreibung  | Text  | nein     | ausfuehrlichere Erklaerung
quelle        | Text  | ja       | woher kam die Datei? csv, json oder xml
rolle         | Text  | nein     | Fachrichtung oder Rolle (z. B. AE)
prioritaet    | Text  | nein     | z. B. hoch, mittel, niedrig
tags          | Liste | nein     | Stichworte fuer die Zuordnung

Das Modell entscheidet ihr selbst - es muss aber fuer alle Quellen und fuer eure Fachzuordnung sinnvoll sein.

MAPPING
-------
Mapping bedeutet: "Welches Feld in Quelle A entspricht welchem Feld in unserem Modell?"

Beispiel:

Feld in CSV-Quelle | Feld in JSON-Quelle | Feld in eurem Modell
Aufgabe            | title               | titel
Beschreibung       | body                | beschreibung
Prioritaet         | priority            | prioritaet
- (fehlt)          | labels              | tags

Wenn ein Feld in einer Quelle fehlt, schreibt ihr None oder einen Standardwert rein.
Das Mapping schreibt ihr zuerst als Tabelle auf Papier oder in Markdown, bevor ihr anfangt zu coden.
Das ist die wichtigste Designarbeit vor der Implementierung.

API UND ENDPUNKTE
-----------------
Eine API (Application Programming Interface) ist eine Schnittstelle, ueber die andere Programme oder Browser
euren Dienst nutzen koennen. Ihr baut eine sogenannte REST-API.

Analogie:
Stellt euch eine API wie die Karte eines Restaurants vor:
- Jeder Eintrag auf der Karte ist ein Endpunkt.
- Der Gast (ein Browser oder ein anderes Programm) schickt eine Anfrage (Bestellung).
- Das Restaurant (eure Anwendung) schickt eine Antwort (Essen, oder eine Fehlermeldung).

Einfache Beispiele fuer Endpunkte:

Methode | Pfad             | Was passiert?
GET     | /userstories     | gibt alle gespeicherten User Stories zurueck
GET     | /userstories/42  | gibt die User Story mit der ID 42 zurueck
POST    | /import/csv      | laedt eine CSV-Datei hoch und liest sie ein
POST    | /classify        | schickt eine User Story rein, bekommt Fachzuordnung zurueck

Wie testet ihr das?
FastAPI erzeugt automatisch eine Seite unter http://localhost:8000/docs, auf der ihr jeden Endpunkt direkt
im Browser ausprobieren koennt. Das nennt man Swagger UI.

API-SKIZZE
----------
Eine API-Skizze ist keine fertige Dokumentation, sondern eine fruehe Planung auf Papier oder in Markdown.
Sie beantwortet:
- Welche Endpunkte brauchen wir?
- Was schicken wir rein?
- Was kommt raus?

Beispiel:
  POST /import/csv
    Eingabe: CSV-Datei als Upload
    Ausgabe: Anzahl importierter User Stories

  GET /userstories
    Eingabe: keine
    Ausgabe: Liste aller User Stories im gemeinsamen Format

  POST /classify
    Eingabe: eine User Story als JSON
    Ausgabe: SDM-Anteil, EvP-Anteil, GiD-Anteil + kurze Begruendung

AUFGABENBOARD
-------------
Ein Aufgabenboard ist eine Uebersicht, wer gerade woran arbeitet und was noch offen ist.
Es verhindert, dass zwei Personen die gleiche Aufgabe machen oder nichts mehr zu tun haben.

Option 1: GitHub Issues (empfohlen fuer dieses Projekt)
Ihr habt bereits GitHub-Accounts. Das Repository, das ihr anlegt, kann direkt GitHub Issues nutzen:
1. Repository anlegen
2. Tab "Issues" oeffnen
3. Fuer jede Aufgabe ein Issue anlegen: kurzer Titel, kurze Beschreibung, wer zustaendig ist
4. Issue schliessen, wenn die Aufgabe fertig ist

Option 2: Microsoft Planner (gut geeignet fuer das Folgeprojekt)
Ihr habt alle M365-Accounts. Microsoft Planner ist Teil davon und funktioniert aehnlich wie ein digitales
Aufgaben-Board (Kanban-Prinzip):
1. Planner ueber Teams oder office.com oeffnen
2. Neuen Plan anlegen (Name = euer Projektname)
3. Buckets anlegen (z. B. "Offen", "In Arbeit", "Fertig")
4. Fuer jede Aufgabe eine Karte erstellen: Titel, zustaendige Person, Faelligkeitsdatum
5. Karte in den richtigen Bucket verschieben, wenn sich der Status aendert

Hinweis fuer das kommende Schuljahr: Im grossen Projektuebergreifenden Projekt werden wir Microsoft Planner
einsetzen. Wer das schon jetzt ausprobiert, ist gut vorbereitet.

Option 3: einfache Aufgabenliste im Teamlog
Falls ein digitales Board zu aufwendig wirkt, reicht auch eine gepflegte Tabelle in doku/teamlog.md.
Wichtig ist nur, dass ihr zu jedem Termin seht: Was ist offen, wer macht was?

DOKUMENTATION - WAS GEHOERT WOHIN?
-----------------------------------
Ihr schreibt drei Arten von Dokumentation. Jede hat eine andere Zielgruppe:

README.md - fuer jeden
Die README ist die erste Datei, die jemand liest, der euer Projekt oeffnet. Sie beantwortet:
- Was macht das Projekt?
- Wie startet man es?
- Was wurde gebaut?
Zielgruppe: Die Lehrkraft, ein fremdes Team, zukuenftige Nutzer.

doku/api.md - fuer Entwickler und Tester
Diese Datei erklaert die API-Endpunkte:
- Welche Routen gibt es?
- Welche Daten muessen rein?
- Was kommt raus?
- Welche Fehlercodes gibt es?
Zielgruppe: Jemand, der eure API benutzen will, ohne den Code zu lesen.

doku/teamdoku.md - fuer das Projekt selbst
Diese Datei dokumentiert eure Arbeit und Entscheidungen:
- Warum habt ihr das Datenmodell so gewaehlt?
- Welche Probleme gab es?
- Wer hat was gemacht?
Zielgruppe: Die Lehrkraft bei der Bewertung und ihr selbst beim Nachschlagen.

AUSGANGSSITUATION
-----------------
Im naechsten Schuljahr arbeitet ihr in groesseren, faecheruebergreifenden Projektteams. Damit ein solches
Projekt spaeter transparent bewertet werden kann, muessen User Stories verschiedenen Buendelungsfaechern
zugeordnet werden - also: Welches Thema steckt in dieser Aufgabe, und fuer welches Fach ist das relevant?

In diesem Abschlussprojekt entwickelt ihr einen ersten, kleineren Prototyp fuer genau diese Aufgabe.

Was sind die Datenquellen?
Als "Datenquellen" dienen Dateien, die ihr selbst erstellt. Sie simulieren Exporte aus echten Werkzeugen:
- eine CSV-Datei (z. B. so wie sie Microsoft Planner exportieren wuerde)
- eine JSON-Datei (z. B. so wie GitHub Issues exportiert werden)
- optional: eine XML-Datei (z. B. ein Export aus einem aelteren Projekttool)

Die Felder in diesen Dateien heissen absichtlich unterschiedlich - das erzeugt die "Heterogenitaet",
die ihr loesen sollt.

ROLLENLOGIK IM TEAM
-------------------
Es gibt keine feste Trennung nach Frontend, Backend und n8n. Stattdessen arbeitet ihr als Produktteam
mit drei Schwerpunkten:

Rolle A - Datenimport und Mapping
- analysiert die Formate (CSV, JSON, XML)
- plant das gemeinsame Datenmodell

Rolle B - Fachlogik und Regelwerk
- entwickelt die Regeln fuer die Fachzuordnung

Rolle C - API, Validierung, Tests und Doku
- erstellt die Endpunkte
- prueft Eingaben und Ausgaben
- sorgt fuer Testprotokoll und Startdokumentation

Wichtig: Jede Person arbeitet schwerpunktmaessig in einem Bereich, aber jedes Teammitglied muss den
Gesamtaufbau erklaeren koennen.

Schritt 1: Team und Name

"Als Kunde moechte ich eine kurze Anleitung erhalten, damit ich die API ohne Rueckfragen nutzen kann."
Das spricht stark fuer GiD.

ARBEITSREGELN FUER EURE ZUORDNUNG
----------------------------------
1. Eine Regel muss begruendbar sein.
2. Ein Ticket darf zu mehreren Faechern passen.
3. Gebt bei Mischfaellen eine gewichtete Empfehlung ab.
4. Nutzt Positiv- und Negativbeispiele.
5. Dokumentiert unklare Faelle offen.

Einfache Gewichtungsidee:
- starker Hinweis = 2 Punkte
- schwacher Hinweis = 1 Punkt
- Gegenhinweis = 0 oder Abzug nach eigener Logik

Beispiel fuer eine Ausgabe:

Fach | Punkte | Begruendung
SDM  | 3      | CSV-Import, Feldmapping, Datenmodell
EvP  | 2      | API-Abruf und Weitergabe
GiD  | 1      | kurze Nutzungsanleitung fuer den Kunden

Wichtig:
Eure Regeln muessen nicht "perfekt intelligent" sein. Sie muessen fuer euer Projekt nachvollziehbar,
konsistent und erklaerbar sein.

PFLICHTDATEIEN

Ihr schreibt drei Arten von Dokumentation - jede fuer eine andere Zielgruppe:

doku/teamdoku.md

- Rollen und Aufgabenverteilung

doku/api.md
Zielgruppe: jemand, der eure API benutzen will, ohne den Code zu lesen.
- alle Endpunkte mit HTTP-Methode und Pfad
- Was wird als Eingabe erwartet?
- Was gibt die API zurueck?
- Fehlerfaelle und Fehlermeldungen
- Beispielanfragen und Beispielantworten

doku/tests.md
- Testfaelle mit Beschreibung
- erwartete Ergebnisse
- tatsaechliche Ergebnisse
- Status: bestanden / fehlgeschlagen

doku/teamlog.md
- was wurde wann von wem bearbeitet
- offene Punkte
- naechster Schritt
